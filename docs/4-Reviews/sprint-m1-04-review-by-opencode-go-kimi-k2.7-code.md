## Executive Summary

`development-protocol-v1.md` is a precise, fail-closed specification for the M1-04 development-only five-fold OOF, working-point, qualification, final-fit, and artifact-publication system. It correctly preserves the MC-only boundary, forbids reading held-out test feature values, requires canonical identity-based fold assignment, and defers test-opening to a later explicit authorization step. It aligns with `FR-001`, the refactor design, and both `AGENTS.md` files.

`sprint-m1-04.md` faithfully scopes the work required to implement the protocol, lists the expected modules and CLI surface, and states the acceptance criteria.

However, **the current `neural/` implementation is far behind the documents**: the required `folds.py`, `qualification.py`, `development.py`, `plots.py`, `test_opening.py`, development-only input reader, and the `higgsml-train develop` subcommand do not exist; the sealed protocol blocks required by Development Protocol §3 are missing from `config/adversarial_mlp_protocol_v1.yaml`; and the existing development loader in `src/training/dataset.py` decodes the full 29-column table (including any held-out `split=test` rows) before rejecting them, which violates the protocol's two-stage reader requirement and the held-out test isolation rule in both `AGENTS.md` files.

**Overall verdict:** The documents themselves are **scientifically sound and consistent**, but they describe a system that is **not yet implemented**. The review findings below separate document-level concerns from implementation-verification gaps.

## Detailed Assessment

### 1. Scientific Safety and MC-only Boundary

- **MC-only:** Both documents correctly restrict inputs to the two bound MC ROOT files and their preprocess offspring. They do not authorize real-data reads.
- **Forbidden features:** The protocol and Sprint preserve the 15-feature classifier input and forbid `m4l`, identifiers, provenance, split, and weight columns as model features, consistent with `neural/AGENTS.md` and the refactor design.
- **Held-out test isolation:** This is the most serious gap. The *documents* correctly state that test feature tokens must never be decoded; the *implementation* currently decodes them because it relies on pandas to read the full preprocess table before filtering. Until the two-stage reader is implemented, M1-04 cannot claim held-out test isolation.
- **No result framing as physics:** Both documents describe outputs as an educational/technical demo, matching both `AGENTS.md` files.

### 2. Internal Consistency

- **Sprint ↔ Development Protocol:** `sprint-m1-04.md` accurately reflects the scope, modules, acceptance criteria, and verification commands of `development-protocol-v1.md`. The only ambiguity is the boundary between `development.py` and the development-only input reader.
- **Development Protocol ↔ FR-001 / Design:** The protocol's fold hashing, working points, qualification rules, tie-break, final-fit epoch selection, and artifact schema are consistent with `FR-001` R4/R6 and the refactor design §8–§10.
- **YAML ↔ Protocol:** The current `adversarial_mlp_protocol_v1.yaml` is **not consistent** with Development Protocol §3 because it lacks the five sealed blocks. This is an implementation gap, not a document inconsistency.

### 3. Correctness Risks

- **Two-stage reader:** Failure to implement this means held-out test feature values enter Python memory during development, violating the primary scientific-safety invariant.
- **Fold assignment:** Without the SHA-256 identity-based fold assignment, OOF scores cannot be guaranteed stable, complete, and free of cross-split contamination.
- **Qualification/working points:** Absent implementation, no candidate can be declared eligible or rejected according to the protocol.
- **Final fit:** Absent final-fit orchestration, an eligible candidate cannot produce the sealed `model.pt` and `scaler.json`.

### 4. Completeness of Implementation

The current `neural/` implementation covers M1-03 primitives (network, losses, single-fold trainer, dataset validation) but is missing almost all M1-04 functionality. Before M1-04 can be considered complete, the following must exist and be tested:

1. Two-stage development input reader with preprocess-run binding.
2. `src/training/folds.py` with canonical identity hashing.
3. `src/training/qualification.py` with AUC/KS/efficiency/working-point logic.
4. `src/training/development.py` orchestrating five candidates × five folds.
5. Final-fit logic and eligible/no-eligible artifact layout.
6. `src/artifacts/plots.py` and development manifest builder.
7. `higgsml-train develop` CLI subcommand.
8. Required unit and integration tests, including the poison-row test.

## Conclusion

`neural/docs/development-protocol-v1.md` and `neural/docs/sprint-m1-04.md` form a **scientifically sound, consistent, and fail-closed plan** for M1-04. However, the **current `neural/` implementation does not yet satisfy them**. The highest-priority remediation is the two-stage held-out-test-isolating reader, followed by the missing protocol YAML blocks, fold-assignment module, qualification module, development orchestrator, final-fit logic, artifact writers, and CLI subcommand.

The documents are approved as the implementation target, but M1-04 should **not be considered implemented** until the Critical and High findings above are resolved and the required tests pass.

No real data or held-out test data were accessed or modified in the preparation of this review. All implementation cross-checks were performed on source files only.
