# Sprint M1-01 文档评审（gpt-5.6-sol）

评审范围为 `docs/3-Plan/sprint-m1-01.md` 与 `docs/1-Requirement/FR-SE-01-sample-efficiency-contracts.md`，并对照 `neural/AGENTS.md`、`docs/research/H4l-Compact-Kinematics-Sample-Efficiency.md`、`docs/research/H4l-Research-Project.md`、`docs/sw-dev/h4l-compact-kinematics-sample-efficiency-development-plan.md`、`docs/sw-dev/artifact-schema.md` 和当前 `src.research` 契约。评审仅判断 M1 软件启动范围；不把正式科学预注册、M2 runtime 或后续实验视为本 Sprint 的交付。

| Severity | Type | Location | Issue | Evidence | Recommendation |
|---|---|---|---|---|---|
| High | Requirement | **F-01** — FR-SE-01 §需求描述 5、§验收要点；Sprint §5.1、§6 | 文档要求“所有需要执行的规则都有版本 ID、未知算法拒绝”，但没有给出这些 ID 的规范值、对应字段路径和允许结构。实现者必须自行命名 subset、pairing、CI、重采样、Q*、capacity、CDF、assessment 和 failure-policy 算法，导致测试 fixture 或首版实现反过来成为事实规范。 | FR 第 32 行只枚举规则类别；Sprint 第 26、40 行要求白名单和版本 ID。上位开发计划 §5.2 也要求这些规则由协议拥有，且 §17 M1 的退出条件是所有科学参数进入严格协议。当前文本不足以据此判定某个完整实例是规范合法还是仅实现者自选。 | 在 FR 中增加规范 schema 表：逐项列出 JSON key path、类型、必填性、固定/可注册属性、首版允许的算法 ID、数值/集合约束及未知值错误。把仍待科学批准的数值与已经可以固定的软件算法 ID 分开；模板中的前者可为 `null`，合法实例中的后者不得由 fixture 临时定义。 |
| High | Correctness | **F-02** — FR-SE-01 §需求描述 2–5、7；Sprint §5.1 | overlay、compact freeze 和调用方身份之间存在重复信息，但“显式交叉绑定”没有列出必须逐项相等或重算的关系。在 M1 明确不验证 receipt/trust-chain 的情况下，仅比较调用方传入的 artifact ID 不能阻止一个内部自洽但与 overlay 科学内容冲突的 freeze payload。 | FR 第 29–32 行分别在 overlay/freeze 中承载 compact 身份、表示、`delta_w68`/来源和 population 历史；第 34 行又明确把 receipt/manifest 信任验证推迟。上位开发计划 §5.2 的 `noninferiority.delta_w68` 与 §5.3 freeze 的 `delta_w68` 重复，且主表示必须包含 freeze 中的唯一 compact。Sprint 第 25 行只写了笼统的“交叉绑定”，测试范围第 29 行也没有点明这些成对篡改。 | 明确列出 M1 的字段级不变量并各加负向测试：overlay 中 compact ID 必须等于 freeze candidate ID；groups、ordered inputs、dimension 必须由 registry 重算且与两侧一致；非劣性 `delta_w68` 及其来源引用必须与 freeze 一致；freeze payload digest 必须重算；传入 artifact ID、payload ID/digest 各自比较什么也要写清。另列出 discovery prepared identity 与后续 learning population 哪些关系只记录、不在 M1 认证，避免错误地要求二者相同。 |
| Medium | Correctness | **F-03** — FR-SE-01 §需求描述 6、§输出；Sprint §6 | `compact_candidate_not_frozen` 的 M1 API 行为未定义。FR 同时说“无 compact freeze 返回”该状态、模块只提供纯解析/验证 API且没有 run/CLI，又规定其余失败抛出 `ResearchError`（退出码 3）；因此无法确定该情况应返回状态对象、抛出 `ResearchStateError`，还是抛出带特定 status 的 `ResearchError`。 | 上位开发计划 §5.3 将该名称定义为“样本效率计划”的终态，§14 又说明批次不得启动；这属于未来 workflow 语义。当前 `src/research/errors.py` 中 `ResearchError.exit_code == 3`，而 `ResearchStateError.exit_code == 0`，两种选择会产生不同的可观察契约。Sprint 验收没有指定应断言哪一种。 | 在 FR 中分别定义 M1 validator 与未来 workflow 的行为。例如明确 validator 对缺失 freeze 抛出的异常类、`status` 和 `exit_code`，并说明 M2/M4 何时把它发布为具名终态；或者定义显式结果类型。为异常类、状态和退出码加一个直接契约测试。 |
| Medium | Documentation | **F-04** — Sprint §3、§6；FR-SE-01 §影响范围、§输出 | M1 要“固化 artifact schema/登记已实现契约”，但 Sprint 只写“相关长期契约文档”，没有指定必须修改的文档及其验收内容，交付可以在未登记两个新 schema 的情况下形式上通过。 | 上位开发计划 §17 M1 明确包含“固化 SampleEfficiencyProtocol、compact freeze 和 artifact schema”；FR 第 24、47 行也要求登记纯 payload 契约与契约文档。当前 `docs/sw-dev/artifact-schema.md` §6 只描述既有 research artifact，并提示未来 schema 需额外验证，没有这两个 M1 schema 的字段、状态或“仅 synthetic 软件验证”标记。 | 在 Sprint 纳入范围中明确列出 `docs/sw-dev/artifact-schema.md`（必要时再列 `software-requirements.md`/索引），并把验收写成：登记两个 schema 的职责、canonical/digest 边界、当前实现状态和验证等级，同时明确不宣称 receipt 发布、M2 runtime、ARM64 authority 或科学数值验证已完成。 |

除上述问题外，文档对 MC-only、assessment 不访问、旧协议与冻结 artifact 不变、Windows synthetic 证据不替代 ARM64/scientific validation，以及 M2—M7 不启动的边界，与 `neural/AGENTS.md` 和上位研究方案一致。
