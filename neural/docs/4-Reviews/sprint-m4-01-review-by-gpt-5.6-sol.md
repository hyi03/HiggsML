# Sprint M4-01 文档评审（gpt-5.6-sol）

| High | Requirement / Executability | **F-01** — `FR-SE-04` §范围 2–6；`sprint-m4-01` §5.1–5.2 | `--plan-only` 无法在现有输入契约下生成其承诺的最终 cell identity。CLI 没有接收既存 `training-subsets` run，执行顺序又把 M2 发布放在 batch plan 之后；但 plan 必须预先包含 M2 plan identity、subset ID、experiment ID、pairing ID 和 stage path。 | M2 的 subset/membership/summary 只有读取 prepared train payload 中的 `physical_weight`/`m4l` 后才能确定（FR-SE-02 §§2、6）；M3 的 `experiment_cell_id` 还绑定 `training_subset_artifact_id`。FR-SE-04 §3 同时禁止 plan-only 加载事件 payload或创建目录，§5却要求输出这些最终身份，§6才在执行阶段发布/重验 M2。单靠 prepared/freeze/overlay 元数据无法重建最终 artifact ID。 | 选择一个无循环的接口并写入 FR/Sprint：推荐增加必需的 `--training-subsets-run`，由独立 M2 步骤先发布；plan-only 只读取并严格重验其 manifest/receipts/plan/ledger，不解码 prepared 事件。若坚持批次内部发布 M2，则把 plan 拆成 preflight coordinate plan 与 M2 后 sealed execution plan，前者不得声称含最终 subset/model IDs；同时分别定义两者 schema、输出和 batch identity。 |
| High | Provenance / Shared-grid binding | **F-02** — `FR-SE-04` §范围 7、9–11 与 §输出；`sprint-m4-01` §5.2 | “每 cell 一个 template run”与“批次只计算一次共同 grid”之间缺少可验证的直接上游。按当前拓扑，template 只绑定 prepared 与自己的 calibration，无法证明 mass edges 是由该批次全部 calibration-success cells 共同生成，也无法拒绝删掉弱 cell 后重签同一模板。 | FR §9 规定 template upstream 仅为 `prepared+calibration`，输出布局为 `cells/<cell-id>/template/`；§7要求 `common_mass_grid()` 对所有成功 cell 只调用一次，§10只让 ledger记录 `grid_id`。M3 的单-cell template builder只验证自己的 prepared/model/calibration lineage，不知道其他 cell。一个普通 `grid_id` 字段或外层 ledger不能替代模板的直接 provenance。 | 新增严格 `sample-efficiency-common-grid` run/schema：upstreams 精确绑定 sealed batch plan、training-subsets及全部且仅 calibration-success runs，payload记录参与/排除 cell、初始 base grid、merge history、最终 edges、terminal状态和自摘要。每个 template run必须直接绑定该 grid run和自己的 calibration（prepared可由二者传递或继续显式绑定）；或者把全部 templates 发布在一个绑定所有 calibrations 的共享 run。reader重算参与集合及 grid ID。 |
| High | Evidence binding | **F-03** — `FR-SE-04` §范围 3、5、9、14；`sprint-m4-01` §2、§5.2 | batch identity没有完整绑定授权其 T1 执行的 gate 与 T1 evidence。plan字段只列 T1 `evidence_id`，未列 gate artifact ID或 T1 canonical digest；单独传入的 `--t1-validation` 也未要求与 gate run中 receipt-bound snapshot逐字节一致。 | 现有 `h4l-t1-validation-v1` 的 `evidence_id` 是普通非空字符串，不是内容摘要；其余 reviewed_by/date/tests 等字段可在保留 evidence_id 时改变。旧 G1 templates run保存自己的 `t1-validation.json`，但 M4同时接收另一条文件路径。FR §14只描述字段值与“同一 prepared/freeze/base”，没有定义 gate stage/file/schema、gate artifact到 compact-freeze 的关系或两份 T1 evidence相等规则；§5的 `batch_id` preimage也省略 gate artifact与 T1 bytes digest。 | plan和所有依赖T1的run显式记录并验证 `gate_artifact_id`、gate stage/path、`t1_evidence_sha256`及完整 snapshot receipt；要求外部 T1文件 canonical bytes等于 gate run内 snapshot。明确 gate 与 compact freeze 的合法连接（例如 freeze的 selection/discovery artifact集合必须包含该 gate/report artifact），不要要求旧 gate凭空拥有后生成的 freeze upstream。所有差异在事件payload、模型构建和输出创建前以binding failure拒绝。 |
| High | Schema / Re-signing resistance | **F-04** — `FR-SE-04` §范围 4–5、9–11、15 与 §输出；`sprint-m4-01` §5.1–5.2 | 文档命名了 plan/ledger/summary 和四层目录，却没有给出足以实现“严格读取、重签后重算”的 schema：根键、cell键、类型、排序、版本、ID preimage、stage/file名、直接 upstream及成功/终态字段均未冻结。 | §15要求未知/缺失/重复键、非有限值、重签身份、错误 upstream/path全部拒绝，但只给出 `h4l-sample-efficiency-batch-plan-v1` 与 `h4l-sample-efficiency-batch-ledger-v1` 的概述；`batch-summary.json`甚至没有 schema名。calibration/template/inference run的正式 stage名、payload文件名、payload schema/digest、lineage验证和 reader API未定义；`common grid ID`、M2 plan identity、W68/AUC“原始输入位置”也没有 canonical表示或摘要算法。不同实现可以生成互不兼容但都声称合规的 artifacts。 | 在 FR 增加字段级 schema表，至少覆盖 batch config、plan、cell descriptor、common grid、cell outcome、ledger、summary，以及 calibration/template/inference/batch run。为每个对象固定 exact keys/types/nullability/order、canonical digest排除字段、ID preimage、文件名、stage、upstream multiplicity/path规则和reader重算责任；指标位置使用绑定 artifact ID + 文件名 + JSON Pointer，而不是自由文本路径。Sprint测试清单逐一映射这些 schema不变量。 |
| High | State machine / Completeness | **F-05** — `FR-SE-04` §范围 6–11、§失败语义；`sprint-m4-01` §5.2、§6 | cell终态、batch级共同网格终态、outer run状态和 `sample_efficiency_completeness` 的关系未定义，导致实现无法同时满足“每个 planned cell恰有一个终态”和“成功cell有四个stage artifact”。 | M2低统计、训练数值终态、calibration/template/inference科学终态发生在不同阶段；共同grid失败会让所有已成功的 model/calibration cell没有 template/inference artifact。文档未说明这些 cell是保留原阶段成功并标记后续 blocked，还是被改写成 batch terminal；也未定义 `planned/deduplicated/complete/terminal` 的互斥与计数公式。外层 stage被称为“完成run”，同时又可能以 `insufficient_statistics`/`template_stat_model_unvalidated` batch terminal结束，而 M5只消费 verified reader结果；`read_run` 对非complete状态需要显式 terminal策略。 | 增加状态转移矩阵：每个初始坐标、去重canonical cell和每个stage outcome的状态/原因/exit code；区分 `cell_status`、`blocked_stage`、`batch_status`。规定预期科学终态是否仍使outer manifest为complete、共同grid失败如何为所有剩余stage写确定记录、哪些状态可被M5 reader消费、binding/unknown失败是否发布失败ledger，以及四个计数的精确重算公式。禁止用后续失败覆盖已发布stage事实。 |
| High | Destructive-operation safety | **F-06** — `FR-SE-04` §范围 2–3、12；`sprint-m4-01` §5.1、§9 | `--clean` 的证明与删除边界仍不足，且与 plan-only 的组合和部分完成批次的处理未定义。递归目标若含已complete的cell run，当前文字可被理解为只检查顶层manifest，从而违反冻结/完成run不可删除规则。 | §12同时要求目标“未发布/失败”“不含complete research manifest”，但未说明是顶层还是整个后代树；M4会先发布多个不可覆盖cell，再可能因binding/unknown错误停止。文档也未规定 `--clean --plan-only` 是usage error、clean删除整个batch还是单个failed/staging目录、匹配plan之外的允许文件清单、Windows junction/reparse point及检查到删除之间的路径替换。`batch-plan.json + batch_id` 本身还是可重签JSON，不足以单独证明目录由该执行创建。 | 明确 `--clean` 与 `--plan-only` 互斥并在任何输入读取前解析；只允许由application service接收显式 `allowed_root` 后执行。删除前对目标及每个祖先/后代解析绝对路径，拒绝symlink/junction/reparse point、根目录、未知entry及任何complete/frozen manifest；使用exclusive创建的batch ownership marker并把它与重算plan、目标绝对路径和失败manifest交叉验证。若部分批次含complete children，规定只删除可证明的staging/failed节点并保留完成run，或整体拒绝clean。测试覆盖Windows路径语义与检查后替换。 |
| Medium | Identity design / Reproducibility | **F-07** — `FR-SE-04` §范围 5、13；总体开发计划 §§5.2、8.3、13.1 | `batch_id` 覆盖 output root和资源上限，把机器/执行配置混入批次科学身份；同一冻结网格在不同路径或 workers设置下会得到不同batch ID，难以在M5比较重放或验证单/多worker等价。 | 总体计划明确路径、worker数、线程数属于run config而不进入科学协议，且要求 workers=1/多worker保持相同计划顺序、cell ID与统计结果。FR §5却把资源上限和output root放入plan并让 `batch_id` 覆盖除自身外全部字段。artifact/run ID本已可记录一次执行的路径、软件与资源，无需让科学批次身份承担该作用。 | 分离 `scientific_batch_id` 与 `execution_plan_id`：前者只绑定双协议、prepared/population/freeze/M2 plan、gate/T1 digest、共同grid规则及canonical cells；后者再绑定输出root、资源和运行参数。ledger同时记录二者，M5按scientific ID判断同一实验，run manifest保留执行身份。至少明确 `experiment_cell_id/pairing_id` 永不受路径或worker变化影响。 |
